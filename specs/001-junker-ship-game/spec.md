# Feature Specification: Junker Ship Wedding Run

**Feature Branch**: `001-junker-ship-game`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "We're building a game completely out of React UI components. The premise: you forgot about your friend's wedding and need to get there ASAP but your space ship is in the shop, so you borrow your uncle's junker. It's constantly threatening to fall apart and it's your job to hold it together for one little trip. Core loop: the user is presented with three sequential scenarios and must choose the right action for each. In each scenario, some component of the ship threatens to fail. The user is presented with a text description of the scenario as well as a set of possible actions to take. The scenario description, available actions, and consequences for each action are generated by an LLM (we'll be using OpenRouter). The available actions have consequences ranging from "problem solved, proceed to next scenario" to "critical error, ship irreparably damaged, game over". Some options allow the user to try again. If the user finishes all three scenarios without breaking down permanently, they win and can start a new game. Different areas of the ship (piloting, engines, life support, etc) are accessed by navigating to different URLs (e.g. `{baseUrl}/piloting`, `{baseUrl}/engine-room`, `{baseUrl}/engine-room/maintenance-hatch`), actions are taken by hitting POST/PUT/DELETE endpoints, and all scenario/ship state is communicated through React UI components."

**Revision input** (2026-09-18): "Generate all available actions up front at game start, then provide them to the LLM as part of its prompt. The LLM generates a scenario with a correct action; these are stored as the active scenario. When the user takes the correct action, the LLM generates success flavor text, grounded in the actions tried before. When the user takes an incorrect action, the LLM generates flavor text that hints at the correct answer and hints that the ship's condition worsened. There is no single 'fatal' action; the LLM decides, with the context of the whole game, whether what the player did was bad enough to end the game. The entire game so far is stored."

## Clarifications

### Session 2026-09-18

- Q: How does the player send an action? → A: Both. In-game controls send the request (and
  show what it is), and players may also send the same requests by hand with external tools.
- Q: Is finding the right part of the ship part of the challenge? → A: Yes. The scenario gives
  only in-story symptoms; the player must work out which action, in which area, fixes it.
  *(Revised: symptoms have no location of their own; only actions do.)*
- Feedback: If AI generation fails, v1 shows a simple error message (e.g., "Can't get a
  response from OpenRouter, try again later"). No pre-written fallback scenarios.
- Feedback: Players sign in. Game progress is saved to the player's account, and each
  player has at most one game at a time.

### Session 2026-09-18 (revision: up-front actions, open-ended consequences)

- Q: Is the set of actions hand-authored or generated? → A: Generated by the AI once per game,
  at game start, and fixed for the rest of that game.
- Q: Who decides whether an action solves the scenario? → A: The game. An action solves the
  scenario only if it is exactly the scenario's stored correct action. The AI only writes text
  and decides game over.
- Q: Are wrong actions sorted into categories (harmless, harmful, etc.)? → A: No. The AI writes
  free-form consequence text; instructions tell it not to punish sensible investigation.
- Q: How is game over decided? → A: Entirely by the AI, for each wrong action, using the whole
  game's history. There is no fixed attempt limit or damage threshold.
- Q: Is ship damage shown outside the story text? → A: No. No meters or component conditions;
  worsening is conveyed only through consequence text.
- Q: Can an action be repeated within a scenario? → A: Deferred. In v1 each action can be taken
  at most once per scenario.
- Q: Do scenarios have a location or a failing component? → A: No. A scenario's symptoms are
  just text. Only actions have locations (an area and an address).
- Feedback: No sub-areas. All ship areas are flat (e.g., no maintenance hatch inside the engine
  room); nesting adds complexity for little payoff.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Survive one ship malfunction (Priority: P1)

A signed-in player starts a new trip and is told, in-story, that they forgot their friend's
wedding and have borrowed their uncle's unreliable ship. The game prepares this ship's full set
of controls and the first malfunction, described only by symptoms (e.g., "the engine
temperature gauge is creeping into the red and something smells like burnt toast"). The player
explores the ship and takes an action. If it is the correct fix, the game reports success in a
way that riffs on what they tried along the way. If not, the game describes what happened,
hints at the real fix, and conveys whether the ship is getting worse; if the action was bad
enough, the ship comes apart and the game is over.

**Why this priority**: This is the core loop. One scenario, fully resolved, is a playable and
demonstrable game on its own; everything else repeats or wraps it.

**Independent Test**: Sign in, start a new game, take several wrong actions and then the correct
one, and confirm each result is shown and the scenario is resolved only by the correct action.
In a separate run, take reckless actions until the game ends in a loss.

**Acceptance Scenarios**:

1. **Given** a signed-in player with no game in progress, **When** they start a new game,
   **Then** they see the premise and the first malfunction's symptoms, and every ship area
   offers its actions.
2. **Given** an active malfunction, **When** the player visits any ship area, **Then** they see
   the symptoms and all of that area's actions, whether or not the correct action is there.
3. **Given** an active malfunction, **When** the player takes the correct action, **Then** a
   success text is shown that reflects the actions already tried in this scenario, and the
   scenario is marked resolved.
4. **Given** an active malfunction, **When** the player takes a wrong action that does not end
   the game, **Then** a consequence text is shown that hints at the correct action and conveys
   the ship's state, the same malfunction stays active, and that action is shown as already
   tried for this scenario.
5. **Given** an active malfunction, **When** the player takes a wrong action and the AI judges
   it bad enough to end the game, **Then** the consequence text is shown, the game ends in a
   loss, and no further actions are accepted for that game.
6. **Given** several wrong actions in the same scenario, **When** each result is shown,
   **Then** the hints become more direct with each wrong attempt.
7. **Given** an active malfunction, **When** the player has not yet taken the correct action,
   **Then** which action is correct is not visible anywhere in the game.

---

### User Story 2 - Complete the three-leg trip and win (Priority: P2)

After resolving a malfunction, the trip continues and a new malfunction appears, with a
different correct action. The ship's history carries forward: damage and mishaps from earlier
legs can make the ship less forgiving later. After the third malfunction is resolved without a
game over, the player arrives at the wedding, sees a victory screen, and can start a new game.

**Why this priority**: Turns the single-scenario loop into a complete game with a beginning,
progression, and an ending.

**Independent Test**: Play through three scenarios, resolving each, and confirm progress is
shown after each, the win screen appears after the third, and a new game can be started from it.

**Acceptance Scenarios**:

1. **Given** scenario 1 or 2 has just been resolved, **When** the player continues,
   **Then** the next scenario begins and progress is shown (e.g., "Leg 2 of 3").
2. **Given** a new scenario has begun, **When** the player views any area, **Then** the same
   set of actions as the previous leg is offered, and actions tried in earlier legs can be
   taken again.
3. **Given** scenario 3 has just been resolved, **When** the outcome is shown, **Then** the
   player sees a victory screen stating they made it to the wedding.
4. **Given** a finished game (win or loss), **When** the player chooses to start a new game,
   **Then** a fresh game begins with a newly generated set of actions and scenarios, and the
   previous game is replaced.
5. **Given** a game in progress, **When** the player looks at any area of the ship, **Then**
   they can see which leg of the trip they are on, the current symptoms, and a log of every
   action taken and its result so far in this game.

---

### User Story 3 - Explore the ship to find the fix (Priority: P3)

The ship is made of distinct areas (e.g., cockpit/piloting, engine room, life support). Each
area has its own address the player can navigate to, and each area offers its own actions. Areas
are flat: none contains another. The player moves between areas
using in-game navigation or by entering an area's address directly, reasoning from the symptoms
and hints about where the fix is likely to be.

**Why this priority**: Exploration is the game's distinctive puzzle, but the core loop can be
demonstrated with a single area.

**Independent Test**: Navigate to each ship area by in-game links and by typing its address
directly; confirm each shows its own actions, and that an unknown address shows a 404 screen
with a way back.

**Acceptance Scenarios**:

1. **Given** a game in progress, **When** the player navigates to any ship area, **Then** they
   see that area's name, its actions, links to every other area, the trip progress, and the
   current symptoms.
2. **Given** a game in progress, **When** the player enters any area's address directly,
   **Then** that area is shown without needing to navigate there from another screen.
3. **Given** any state, **When** the player navigates to an address that is not a ship area,
   **Then** a 404 screen is shown with a link back.
4. **Given** a signed-in player with no game in progress, **When** they navigate directly to a
   ship area, **Then** they are offered a way to start a new game.

---

### User Story 4 - Sign in and pick up where you left off (Priority: P4)

A player creates an account or signs in. Their game, including every action taken and every
text shown, is tied to their account, so they can leave mid-trip and come back later, on the
same or another device, and continue exactly where they stopped. Each player has at most one
game at a time.

**Why this priority**: Needed for saved progress and for identifying who sent an action, but the
game loop can be demonstrated with a single test account.

**Independent Test**: Sign in, start a game, take a wrong action and then resolve one scenario,
sign out, sign back in (optionally on another browser), and confirm the game resumes on leg 2
with the same log text as before.

**Acceptance Scenarios**:

1. **Given** a visitor who is not signed in, **When** they open any game screen, **Then** they
   are asked to sign in or create an account first.
2. **Given** a signed-in player with a game in progress, **When** they sign out and sign in again
   from any device, **Then** their game resumes at the same point, with the same actions,
   symptoms, and log text.
3. **Given** a signed-in player with an existing game (in progress or finished), **When** they
   start a new game, **Then** the existing game is replaced and they still have exactly one game.
4. **Given** two different players, **When** each plays, **Then** neither can see or affect the
   other's game.

### Edge Cases

- **Generation fails, times out, or returns unusable content** (at game start, for a new
  scenario, or for an action's result): the player sees a simple error message such as "Can't
  get a response from OpenRouter, try again later" and a way to retry. No progress already made
  is lost.
- **Result generation fails after the player acts**: the action is not recorded at all; the
  player can take it again (or another action) once the service responds. An action never counts
  without its result being shown.
- **Generation is slow**: the player sees an in-story waiting state rather than a blank screen.
- **Player can't work out the fix**: every area stays reachable, hints become more direct with
  each wrong attempt, and there is no time limit. Whether the ship survives the search is up to
  the AI's judgment.
- **Player tries every action**: each action can be tried once per scenario, and the correct
  action is always among them, so a player who survives long enough will always find it.
- **Player tries an action already tried in this scenario** (double-submit, back button,
  refreshing after acting, resending by hand): no new attempt is recorded; the existing result
  for that action is shown again.
- **Request matches no action**: rejected with an error message; game state is unchanged and
  it does not count as an attempt.
- **Player acts after the game ends**: the action is rejected and the player is pointed to start
  a new game.
- **Player uses two tabs or two devices at once**: both reflect the same single game. Actions are
  applied one at a time in the order received; each result takes all earlier ones into account,
  and each screen reflects all of them on its next load.
- **Player acts while a previous action's result is still being generated**: the new action
  is rejected. Actions are only valid when it's the player's turn, and the server tracks when
  an action is being evaluated. The player can retry once they see feedback that generation is
  complete.
- **Session expires mid-game**: the player is asked to sign in again and then returns to their
  game unchanged.
- **Generated text contains inappropriate content**: generation is instructed to keep content
  light-hearted and family-friendly; content that fails this check is treated as a generation
  failure.

## Requirements *(mandatory)*

### Functional Requirements

**Accounts**

- **FR-001**: Players MUST be able to create an account, sign in, and sign out.
- **FR-002**: All game screens and actions MUST require a signed-in player.
- **FR-003**: Each player MUST have at most one game at a time; the game belongs to exactly one
  player, and the game shown is always "that player's current game".
- **FR-004**: A player's entire game MUST be saved to their account, including its actions,
  scenarios, and every attempt with the exact text shown, so it can be resumed after reloading,
  signing out, or switching devices, and previously shown text never changes.
- **FR-005**: A player MUST NOT be able to see or change another player's game.

**Game lifecycle**

- **FR-006**: Players MUST be able to start a new game from the game's home screen and from any
  win or loss screen.
- **FR-007**: Starting a new game MUST replace the player's existing game, if any.
- **FR-008**: The home screen MUST present the premise: the player forgot their friend's wedding,
  their own ship is in the shop, and they have borrowed their uncle's junker.
- **FR-009**: A game MUST consist of exactly three sequential scenarios; only one scenario is
  active at a time.
- **FR-010**: The game MUST end in a win when the third scenario is resolved, and in a loss when
  the result of a wrong action declares game over.

**Ship actions**

- **FR-011**: When a new game starts, the game MUST generate, using an AI language model, the
  complete set of actions available on the ship for that game. The set MUST NOT change for the
  rest of the game.
- **FR-012**: Each action MUST have a unique identifier, a short label, a request type (**do**,
  **set**, or **remove**), and a target address beneath exactly one ship area. The request type
  MUST suit the action's meaning (e.g., removing a clogged filter is a "remove").
- **FR-013**: Within a game, each action MUST be uniquely identified by its request type and
  target address, so that any request maps to at most one action.
- **FR-014**: Every ship area MUST offer at least 3 actions, and the full set MUST contain at
  least 10 actions.
- **FR-015**: Every area MUST offer all of its actions whenever a scenario is active, regardless
  of which action is correct.

**Scenarios**

- **FR-016**: Each scenario MUST be generated by the AI from the game's full set of actions and
  the game's history so far, and MUST consist of symptom text and exactly one correct action
  chosen from that set.
- **FR-017**: The symptom text MUST NOT name the correct action or its area directly.
- **FR-018**: The three scenarios in a game MUST each have a different correct action.
- **FR-019**: The identity of the correct action MUST NOT be discoverable by the player before
  it is taken.
- **FR-020**: Each scenario MUST be stored as soon as it is generated and shown unchanged until
  it is resolved or the game ends.

**Taking actions and consequences**

- **FR-021**: An action MUST resolve the active scenario if and only if its identifier exactly
  matches the scenario's correct action. The AI MUST NOT decide whether an action is correct.
- **FR-022**: When the correct action is taken, the AI MUST generate success text informed by
  the actions already tried in that scenario and the game so far. Taking the correct action MUST
  NOT end the game in a loss.
- **FR-023**: When a wrong action is taken, the AI MUST generate consequence text that (1) hints
  at the correct action and (2) conveys the ship's condition, including any worsening, and MUST
  decide, using the whole game's history, whether the game is over.
- **FR-024**: Wrong-action hints SHOULD become more direct with each further wrong attempt in the
  same scenario.
- **FR-025**: The AI SHOULD not punish sensible investigation. Cautious or
  diagnostic actions SHOULD yield useful information without worsening the ship. Game over MUST
  be reserved for actions that repeatedly fail to communicate understanding of hints or are
  reckless in light of everything that has happened.
- **FR-026**: Each action MUST be taken at most once per scenario. Actions already tried in the
  active scenario MUST be shown as tried and MUST NOT be offered again until the next scenario.
  A repeated request for one MUST show its existing result and record nothing new.
- **FR-027**: An action MUST count as an attempt only once its result has been generated and
  stored. If result generation fails, nothing about the action is recorded.
- **FR-028**: Actions in the same game MUST be processed one at a time, so each result accounts
  for every earlier attempt.
- **FR-029**: A request MUST be accepted only if it matches one of the game's actions, that
  action has not been tried in the active scenario, and the game is in progress. Otherwise it
  MUST be rejected with an error message, no state change, and no attempt counted (except as
  in FR-026).
- **FR-030**: After an action, the player MUST see its result text and whether the scenario was
  resolved, continued, or the game ended. Every area MUST reflect the updated game state on its
  next load.
- **FR-031**: Every game screen MUST give access to a log of all attempts so far in the game, in
  order, with their result text.
- **FR-032**: Ship damage MUST be conveyed only through story text; there MUST be no health
  meter, damage counter, or component condition display.

**Generation reliability and safety**

- **FR-033**: Generated content MUST be checked before being stored or shown. The action set
  MUST satisfy FR-012 to FR-014; each scenario MUST satisfy FR-016 to FR-018; each result MUST
  contain text and, for wrong actions, a game-over decision. Content that fails MUST be treated
  as a generation failure.
- **FR-034**: When generation fails, the player MUST see a simple error message (e.g., "Can't
  get a response from OpenRouter, try again later") and a way to retry. Progress already made
  MUST be kept.
- **FR-035**: While content is being generated, the player MUST see an in-story waiting state
  rather than a blank or broken screen.
- **FR-036**: The AI MUST receive only game-generated content and the player's choices from the
  game's action set; free text supplied by a player MUST NOT reach the AI.
- **FR-037**: Generated content MUST be light-hearted and suitable for all ages, in keeping with
  a comedic "hold the junker together" tone.

**Ship areas and navigation**

- **FR-038**: The ship MUST be divided into named areas, each reachable at its own
  human-readable address, including at minimum: piloting, engine room, and life support.
  Areas MUST NOT be nested; every area is at the top level of the ship.
- **FR-039**: Each area MUST display its actions, links to every other area, the current trip
  progress, and the active scenario's symptoms.
- **FR-040**: Every area MUST be reachable through in-game navigation from every other area.
- **FR-041**: Navigating to an address that is not a ship area MUST show a 404 screen with a link
  back.

**Sending requests**

- **FR-042**: Each area MUST offer in-game controls for its actions.
- **FR-043**: The game MUST tell signed-in players how to identify themselves on requests sent by
  hand. Requests without valid player credentials MUST be rejected.

**Presentation**

- **FR-044**: The game MUST be fully playable using only a keyboard, and outcomes (resolved,
  continued, game over) and tried actions MUST be communicated with text, not color alone.
- **FR-045**: The game MUST be fully playable on mobile devices or small screens.

### Key Entities

- **Player**: A person with an account. Has at most one game.
- **Game**: One playthrough belonging to exactly one player. Has a status (in progress, won,
  lost), its action set, the ordered list of three scenarios, the index of the current scenario,
  and the ordered history of attempts.
- **Ship Area**: A fixed, named location on the ship with an address. Areas are not nested.
- **Action**: A choice available throughout one game, generated at game start. Has an
  identifier, a label, a request type (do / set / remove), and a target address within one area.
- **Scenario**: One malfunction. Has symptom text, a hidden correct action, and a status
  (pending, active, resolved).
- **Attempt**: One action taken during a scenario. Records the action, its order in the game,
  the result text shown, and whether it resolved the scenario, continued it, or ended the game.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A new player can go from creating an account to reading their first malfunction's
  symptoms in under 2 minutes, with no instructions beyond what the game shows.
- **SC-002**: A full three-scenario game can be completed in under 15 minutes.
- **SC-003**: When the AI service is available, a new game (its action set and first scenario)
  is ready to play within 15 seconds of starting it in at least 95% of games, and each later
  scenario within 10 seconds.
- **SC-004**: When the AI service is available, an action's result is shown within 8 seconds of
  taking it in at least 95% of actions.
- **SC-005**: When the AI service is unavailable, 100% of affected attempts show the error
  message within 30 seconds, with no lost progress and no action counted without its result.
- **SC-006**: 100% of scenarios shown to players have exactly one correct action that exists in
  the game's action set, and 100% of scenarios are resolved by that action and no other.
- **SC-007**: 0 screens or responses reveal which action is correct before it is taken.
- **SC-008**: In playtesting, at least 80% of players find the correct action without outside
  help, at least 80% of players who lose agree the loss made sense given what they had done, and
  at least 80% of players who finish a game start another.
- **SC-009**: Two consecutive new games present different action sets and scenario text at least
  90% of the time.
- **SC-010**: 100% of ship areas can be reached both via in-game navigation and by entering their
  address directly.
- **SC-011**: For every action, sending it by hand and using the in-game control produce the same
  result, and 100% of previously shown result text is identical after a reload or device switch.

## Assumptions

- Account sign-in uses email and password; there are no roles beyond "player", and no
  leaderboards or social features.
- Only each player's current game is kept. Starting a new game replaces the previous one, so
  there is no game history across games. A finished game stays viewable until it is replaced.
- The set of ship areas is fixed and hand-authored; the AI generates the actions within those
  areas, the scenarios, and the results, but never new areas.
- There is no score, timer, attempt limit, or damage threshold. Game over is decided only by the
  AI's judgment of each wrong action in the context of the whole game; the ship's history
  carries over between legs.
- Hints are given only through wrong-action results; there is no separate hint feature.
- Repeating an action within a scenario is out of scope for v1 and may be added later.
- A scenario's correct action may be one that was tried (wrongly) in an earlier leg.
- Results of requests sent by hand appear in the game on the next page load; live updating of
  already-open screens is not required.
- English only; desktop and mobile browsers are both supported.
- Depends on an external AI text-generation service (OpenRouter, as specified). There is no
  offline or pre-written fallback in v1. Service credentials stay private to the game operator
  and are never exposed to players.
